# 分页参数缺少统一上限

## 问题现象

评价、订单、套餐、商家申请、核销记录、失败任务和 Elasticsearch 搜索等多个入口将外部 `current`、`size` 直接传给分页组件。调用方可以提交负页码或超大 `size`，造成参数异常、数据库大结果集查询或 Elasticsearch 高内存消耗。

## 排查过程

1. 扫描后端所有 `new Page<>(current, size)` 和 `PageRequest.of(page - 1, size)` 调用。
2. 确认 7 个文件中的多个业务入口没有对页码和每页数量做统一规范化。
3. 检查失败任务接口，确认虽然有默认值，但没有限制调用方传入的超大 `size`。
4. 设计无外部依赖的分页工具，统一处理 MyBatis-Plus 和 Spring Data 的页码语义。

## 根因

分页校验分散在控制器和服务中，没有统一的边界策略；部分接口依赖前端默认值，忽略了接口参数可被直接构造。

## 解决方案

1. 新增 `PageUtils`：页码最小为 1，默认每页 10 条，最大每页 50 条。
2. 为 Spring Data 提供安全的从 1 开始到从 0 开始的页码转换。
3. 在套餐、订单、评价、商家申请、商家搜索、核销记录和失败任务入口统一应用规范化逻辑。
4. 新增单元测试覆盖空值、负数、合法值、超大值和零基页码转换。

## 验证结果

- 后端扫描已不存在直接使用外部 `new Page<>(current, size)` 或 `PageRequest.of(page - 1, size)` 的调用。
- `mvn -q -Dtest=PageUtilsTest test`：通过，共 6 个测试方法。
- `mvn -q -DskipTests compile`：通过。

## 关键收获

将分页边界收敛到一个无状态工具，可以同时消除非法页码和超大查询风险，并避免每个业务服务重复实现不一致的校验逻辑。
