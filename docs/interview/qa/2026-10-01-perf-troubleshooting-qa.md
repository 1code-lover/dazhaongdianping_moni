# 压测性能问题排查三连（面试 Q&A）

- 类型：性能排查 / 工程方法论
- 日期：2026-10-01
- 关联报告：`docs/reports/2026-10-01-loadtest-baseline-report.md`
- 背景：项目压测治理过程中连续遇到的三个真实问题，完整呈现了"假设 → 证伪 → 定位"的排查路径

---

## Q1：压测数据显示某接口 219ms 且优化代码后没有改善，你怎么排查？

**A：** 这个案例的最终结论是**测量本身被污染**，它教会我压测的第一原则是"先信任工具，再怀疑工具"。

过程：复测发现 `/blog/hot` 优化 N+1 后毫无改善，从应用侧逐层下钻——jstack 抓线程发现阻塞在 MySQL socket 读 → `performance_schema` 发现 `COUNT(*)` 语句平均 102ms → 但用 mysqlslap 压同样的语句只要 0.5ms。就在怀疑"环境怪象"时，注意到系统 load 高达 35 但 CPU 空闲 92%——负载和 CPU 矛盾说明有隐藏负载源。`ps` 找到六个 `python3 -` 孤儿进程：之前排查用的后台并发脚本没有写退出条件，变成无限循环持续打满 CPU，**所有"干净复测"数据全是脏的**。

方法论沉淀：
1. 后台压测脚本必须有退出条件，测完 `ps` 检查残留
2. load average 与 CPU 利用率背离 = 有看不见的任务（D 状态/其他租户/孤儿进程）
3. 绝对数值不可信时，找两个独立测量手段交叉验证（客户端计时 vs 服务端 performance_schema）

## Q2：一个 12 行表的 `COUNT(*)` 在并发下要 100ms，同库同连接的其他查询只要 1.3ms，怎么定位？

**A：** 这是典型的"单点慢查询"，我做了六轮排除，每轮都有实证：

| 假设 | 验证方式 | 结论 |
|------|----------|------|
| JDBC 驱动太老（5.1.47） | 换 8.0.33 复测 | ❌ 同样 99ms |
| 连接池/Hikari/MyBatis 层 | 裸 JDBC 20 线程复现 | ❌ 与应用无关 |
| 表统计信息过期 | ANALYZE TABLE 后复测 | ❌ 无效 |
| 测量污染（CPU 竞争） | 清理孤儿进程，load 0.36 复测 | ❌ 稳定复现 |
| 回环网络本身 | 裸 TCP echo 20 并发 0.88ms | ❌ 网络无辜 |
| 锁/长事务 | history list = 0，无 MDL | ❌ |

最后拿到的规律是：**并发梯度相变**（1 线程 0.55ms → 2 线程 0.82ms → 5 线程 37ms）+ **表特异性**（单页表 tb_blog 慢、多页表 tb_user 快）+ 走 Unix socket 全部正常。综合判定为云主机环境级问题（疑似虚拟化与 InnoDB 单页并发读的交互），与业务代码无关。

**处理方式：** 应用层规避——MyBatis-Plus 分页默认的 `COUNT(*)` 用 `searchCount(false)` 消除（前端本就不需要总数），N+1 一并治理。这个案例的面试价值在于：**排查不是为了找到"终极根因"，而是为了做出正确的工程决策**——在 4C 演示机上继续深挖内核不值得，把查询从热路径上拿掉才是正解。

## Q3：给服务器申请 Let's Encrypt 证书，ACME 验证报 403，但本地测试同样的 URL 返回 200，为什么？

**A：** 这个案例的关键动作是**查 nginx 访问日志打破"全有或全无"的思维定式**。

Let's Encrypt 从 2021 年起启用多视角验证（Multi-Perspective Validation），会从全球多个网络位置同时校验域名。查日志发现：一个 LE 验证节点（23.178.112.108）的请求**到达了我们的 nginx 且返回 200**，但 LE API 却报告 403——说明**不同视角解析到了不同的地方**。

根因：为了零成本用了 `sslip.io` 的 IP 转域名服务，LE 的部分验证视角使用的解析器对该域名返回了被污染的结果（sinkhole 返回 403），另一部分解析正常。这种"部分成功部分失败"的表现是所有免费 IP 域名服务的通病。

**决策：** 放弃免费域名路线，运维手册记录结论（买个 ¥10/年 的便宜域名 + certbot 即可，nginx 已就绪）。教训：**自动化系统的验证失败要先问"验证方看到了什么"，日志里的一次成功比十次失败重试更有信息量**。

## 串场总结（可用于"介绍一个你排查过的最难问题"）

三个案例可以串成一条主线：**性能优化的尽头是测量，测量的尽头是环境，环境的尽头是工程决策**。从"优化无效"到"数据是假的"，从"语句慢"到"机器怪"，从"证书失败"到"DNS 污染"——共同点是都用日志和多视角交叉验证避免了在错误的方向上深挖。
